# N100 관리 에이전트 인계서 · Vercel 전송량 일일 확인

**인수할 작업:** N100에서 하루 한 번 Vercel 팀 `woong-ts`의 최근 30일 전송량을 읽고, 한도에 가까워지거나 조회가 계속 실패할 때 운영자에게 알린다. 정상 범위에서는 조용히 기록만 남긴다. 2026-11-04 현재 문서 인계 단계이며 N100 감시 작업은 설치 전이다.

## 담당 경계

| 담당 | 맡을 일 |
| --- | --- |
| 포털 프로젝트 `Cho-WH/scope-portal` | 감시할 팀·지표와 경고 기준을 정한다. 경고를 받은 뒤 어느 사이트나 파일의 사용량이 늘었는지 확인하고 배포·도메인·DNS·호스팅 전환을 결정한다. [공통 배포 운영 기준](deployment.md) |
| N100 관리 에이전트 | 자신의 서버 관리 저장소에 수집기와 예약 설정을 두고 설치·실행·상태 보존·알림 전달·재인증·중지를 관리한다. Vercel에서는 Usage 화면만 읽는다. Cloudflare나 배포용 토큰은 필요 없다. |
| 운영자 | 최초 로그인과 필요 시 2단계 인증을 직접 수행하고, 알림을 받을 기존 채널과 수신 대상을 정한다. |
| 센서 실험실 프로젝트 | 실험실 앱과 파일을 관리한다. 실험실에서 사용량이 늘었다는 근거가 있을 때 포털에서 원인 확인을 요청한다. |

## N100에서 설정할 순서

1. **실행 위치를 정한다.** N100은 Ubuntu 24.04 LTS, x86_64, 시간대 `Asia/Seoul`이며 Docker와 cron이 활성 상태였다. 기존 서버 관리 방식을 우선한다. 기본안은 Playwright와 Chromium이 든 일회성 컨테이너다. 이미지와 Playwright 버전을 맞춰 고정하고 서버 재시작 후에도 프로필과 마지막 상태가 남도록 전용 로컬 디렉터리를 마운트한다. [Playwright 컨테이너 안내](https://playwright.dev/docs/docker)
2. **전용 브라우저 프로필로 로그인한다.** 운영자가 N100의 로컬 화면 또는 SSH 터널로 제한한 브라우저에서 Vercel에 로그인한다. 자동 실행도 같은 프로필을 사용한다. 프로필은 세션 쿠키를 담고 있으므로 실행 계정만 접근하게 하고 Git, 채팅, 인수 보고서에는 넣지 않는다. [인증 상태 보관 안내](https://playwright.dev/docs/auth)
3. **먼저 한 번 읽어 대조한다.** Vercel에서 팀 `woong-ts` → **Usage** → **Last 30 days** → **All projects** → **Fast Data Transfer**를 선택한다. 대시보드에서 운영자가 보는 값과 수집기가 읽은 사용량·단위·한도를 대조한다. 두 앱은 같은 팀에 있으므로 팀 값을 한 번만 읽는다. `Fast Origin Transfer`, 청구 금액, 프로젝트별 값의 중복 합산은 제외한다. 팀·기간·지표를 식별할 수 없으면 실패로 기록한다. 공식 청구 API는 이 팀에서 `404 costs_not_found`를 반환한 이력이 있다. [Vercel Usage 안내](https://vercel.com/docs/pricing/manage-and-optimize-usage)
4. **예약과 알림을 연결한다.** 수동 실행이 맞으면 서버 시간 기준 `0 9 * * *`로 등록한다. 절대 경로의 실행 스크립트에 `flock`과 제한 시간을 적용해 겹친 브라우저가 같은 프로필을 열지 않게 한다. 알림은 운영자가 지정한 기존 채널로 보내고, 본문은 팀·조회 기간·사용량/한도·관측 시각 또는 실패 사유 한 줄이면 된다.

## 기록과 알림 규칙

현재 기준은 팀 전체 **80GB 이상 주의, 95GB 이상 높은 사용량**이다. 화면의 원래 수치와 단위를 보존하고 같은 단위로 환산해 비교한다. 한도가 기존 100GB에서 달라지면 새 한도를 함께 보고해 포털에서 기준을 조정할 수 있게 한다.

| 상황 | 처리 |
| --- | --- |
| 80GB 미만 | 마지막 정상값과 조회 시각을 갱신한다. 정기 알림은 보내지 않는다. |
| 80GB 또는 95GB 경계를 위로 통과 | 도달한 단계에서 한 번 알린다. 78GB에서 96GB로 뛰면 95GB 알림 한 건만 보낸다. 이후 해당 경계 아래로 내려갔다가 다시 넘으면 새 경고로 처리한다. 첫 정상 조회가 이미 경계 이상이어도 같은 규칙을 쓴다. |
| 로그인 만료, 화면 변경, 시간 초과, 단위 누락 | 마지막 정상값을 유지한다. 실패한 예약일이 이틀 연속이면 원인과 마지막 성공 시각을 한 번 알린다. 같은 날 재시도는 하루로 계산한다. 정상 조회가 돌아오면 실패 상태를 해제한다. |
| 알림 발송 실패 | 보낼 경고를 로컬 상태에 남기고 다음 실행에서 재시도한다. 발송이 성공한 뒤에만 해당 경고를 전달 완료로 표시한다. |

상태 파일은 조회일, 마지막 정상 관측, 사용량 단계, 연속 실패 일수, 마지막 전달 또는 미전달 경고만 보존하면 된다. 실패 로그에는 쿠키·토큰·대시보드 HTML을 기록하지 않는다.

## 인수 확인과 회신

- **실제 화면 확인:** 로그인된 세션에서 팀·기간·지표가 맞고, 브라우저를 닫았다가 예약과 같은 명령으로 다시 읽어도 값이 일치한다.
- **알림 동작 확인:** 모의 입력 `79 → 82 → 83 → 96GB`에서는 82와 96에서만 알림이 생긴다. 로그인 실패를 서로 다른 이틀로 모의 입력하면 두 번째 날에만 경고가 생긴다. 실제 전송량을 늘릴 필요는 없다.
- **운영 인수:** 첫 예약 실행 결과를 확인한 뒤 아래 항목을 포털 담당자에게 회신한다. 설치 직후에는 ‘수동 확인 완료, 첫 예약 실행 대기’로 구분한다.

| 회신 항목 | 내용 |
| --- | --- |
| 작업 위치 | N100 관리 저장소·커밋, 설치 경로, cron 등록 위치 |
| 관측 결과 | 마지막 성공 시각(KST), 팀·기간, 표시 사용량/한도, 대시보드와 대조 결과 |
| 운영 방법 | 수동 실행·로그 확인·재인증·예약 중지 방법, 알림 채널 이름과 시험 결과 |
| 인계 상태 | 첫 예약 실행 결과, 남은 문제, 운영자 조치가 필요한 항목 |

경고가 오면 N100은 관측값을 전달하고, 포털이 대응을 판단한다. 재인증이 잦아 관리 부담이 커지면 N100은 예약 중지를 제안하고 포털은 기본 알림과 수동 확인으로 돌아갈지 결정한다.
